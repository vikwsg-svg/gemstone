Authentication and sandbox

Two kinds of keys.

  • gsk_test_ keys return example results for every product. Every response says synthetic_data: true.
  • gsk_live_ keys run against the production engine.
  • Send keys as Authorization: Bearer <key>. Keys are scoped per product.
  • Errors always have the same shape: {"error": {"code", "message"}}.
Safe by design

Retries, versions and floors.

  • Idempotency keys on every POST, for every product: a retried request returns the original result and is billed once.
  • Versioned results: every response is stamped with the scan model; pin one per request or per account.
  • No guessing: the price is withheld, with the reason, when the item can’t be identified or fewer than five comparables are found.
  • Long scans return 202 with status: processing; retrieve the scan to get the result.
  • Sale or asking price on every comparable, via price_type.

Batch

A spreadsheet in, a spreadsheet out.

Every product takes a CSV with one item per row (photo links, plus anything you already know): revalue a portfolio with the Scan API, route a back-of-house queue with Intake, or screen a claims backlog with Verify. Poll the job, then download one result row per item.

Webhooks

Get told, don’t poll.

  • Events: intake.item.completed, verify.check.completed, verify.check.flagged and batch.completed
  • Signed: GemstoneAI-Signature: t=<unix>,v1=<hex>, an HMAC-SHA256 of the timestamp and raw body with your secret
  • Small payloads: a summary of the result and its path, never photos
  • Retried on failure, with a delivery log you can read and retry from
Console

For the people who work the queue.

A web app on the same API at /enterprise/v1/console/: the intake station for associates, the Verify review queue for analysts, and settings for your rules and webhook. Sign in with a sandbox key to try it with example results.
